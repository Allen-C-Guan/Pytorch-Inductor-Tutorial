## 3.0 本章俯瞰

前两章回答了"为什么编译"(详见第 1 章)与"编译服务于怎样的运行时"(详见第 2 章)。可当你真正打开 vLLM 源码,面对 compilation/ 目录下的十几个文件、模型目录里几十个带装饰器的类、配置里成串的枚举,一个很实际的问题随之而来:这一切从哪里读起?几十个机制各自行事,它们之间谁先谁后、谁给谁供货、在服务进程的一生中各自醒着多久?答案预告:全部机制可以装进一张五层架构图——模型层、前端、中端、后端、执行层,每层只认一份输入产物、只交一份输出产物;而这一切几乎全部发生在进程启动的那几十秒里,真正对外服务的每一步只剩查表与重放。本章交付三样东西:一张标注产物流向的总览大图、一条"编译发生在什么时候"的启动时间轴、一把把任何机制定位到"编译期还是运行时、图内还是图外、静态还是符号"的坐标系。此后每一章,都能在这张图上找到自己的格子。

## 3.1 最小前置知识

- **FX GraphModule(FX 图模块)**:dynamo 把 Python forward 捕获成的图表示,节点是一次次算子调用,节点 meta 里带 **fake tensor(假张量,只含 shape/stride/dtype 元数据不占数据)**。它是 L2 交给 L3 的唯一通货,捕获细节详见第 5 章。
- **backend(编译后端)**:torch.compile 的可插拔参数——任意"接收 FX 图与示例输入、返回可调用对象"的函数都可以。vLLM 的主角 **`VllmBackend`(vLLM 编译后端)** 就是一个 backend,详见第 8 章。
- **`@support_torch_compile`(编译支持装饰器)**:`vllm/compilation/decorators.py` 提供的类装饰器,把模型类挂到一个特殊基类上并声明哪些输入维是符号维;它是 L1 与 L2 之间的接缝,详见第 5 章。
- **CUDA Graph capture/replay(捕获/重放)**:把一段 GPU 工作录成静态图、此后一次调用整段重放;机制动机见第 1 章,运行时细节详见第 12 章。
- **num_tokens(本步总 token 数)**:第 2 章的结论——调度与执行的全部动态性被压缩进这一个整数,它也是编译图唯一的符号维。

## 3.2 设计思想与设计哲学

**分层不是画图习惯,而是产物契约。** 五层中每一层都只向上游要一份明确类型的产物、向下游交一份明确类型的产物:L1 交出"普通 nn.Module 的 forward",L2 交出"单张 FX 图",L3 交出"切分后、可编译子模块已被编译产物替换的 split_gm",L4 交出"每 **piece(片段)** × 每 range 一个 compiled artifact",L5 交出"serve 期每步调用的 callable"。层与层之间不共享内部状态——想理解任何一层,只需读它的输入契约与输出契约。这是 P5(显式优于隐式)在架构层的落点,也是本书敢按层组织章节的前提:后续十二章,不过是把这张图逐格放大。

【哲学时刻】**时间轴比机制清单更重要。** 回扣全书叙事主线:decode 是 CPU/launch bound → 必须消灭 Python 开销 → 代价是编译 → 编译代价是启动时间 → 所以全部编译前置+缓存 → 所以敢丢 guards、敢一次 trace、敢去泛函化。这条链的倒数第二环"全部编译前置"不是某个函数的实现细节,而是整个栈的工期纪律,并被固化成四条不变量,每条都能指认到源码行号:(a) dynamo 只 trace 一次——guards 全丢(`wrapper.py:120-122`(`skip_all_guards_unsafe`)),`set_stance("fail_on_recompile")` 作运行时断言(`vllm/compilation/wrapper.py:195`);(b) 启动期编完一切——`PiecewiseBackend` 在构造函数里就把所有 range 编完(`vllm/compilation/piecewise_backend.py:189-190` 调 `compile_all_ranges`);(c) capture 结束即锁定——`set_cudagraph_capturing_enabled(False)`(`vllm/v1/worker/gpu_model_runner.py:6900`),此后意外捕获直接 raise;(d) serve 路径零编译、零捕获、零 Python 编排。其中 (b) 还有结构性守卫:`monitor_profiling_run`(`vllm/compilation/monitor.py:62-84`)在进入前记录后端编译计数、结束后断言期间无任何新增编译(在 AOT 路径被套用,`decorators.py:570`、`:669`)。不变量不是注释,是 assert——P1(compile once, run forever)与 P2(不变量换性能)因此是可以在行号上逐条指认的工程事实,而非口号。

逐层看流水线产物句式:

**L1 模型层。** 上游给我模型类定义与权重(`vllm/model_executor/models/*.py`,如 `llama.py:334-343` 处 `@support_torch_compile(dynamic_arg_dims=...)` 声明唯一符号维)→ 我用 **`support_torch_compile`(编译支持装饰器,`vllm/compilation/decorators.py:118`)** 把 `TorchCompileWithNoGuardsWrapper` 注入模型基类、记录符号维声明(实现于 `decorators.py:331`(`_support_torch_compile`))→ 产出普通 nn.Module forward——表面上什么都没发生,编译被刻意推迟到首次调用。消费该装饰器的模型文件已有 120+ 个(`qwen3_next.py:589`、`olmoe.py:266`、`jamba.py:302` 等)。

**L2 Dynamo 前端。** 上游给我首次 forward 调用(启动期由 `_dummy_run` 发起,`vllm/v1/worker/gpu_model_runner.py:6156` 的 `self.model(...)`)→ **`TorchCompileWithNoGuardsWrapper`(无守卫编译包装器,`vllm/compilation/wrapper.py:47`)** 在模型实例化时就已经用 `torch.compile(fullgraph=True, dynamic=False, backend=...)` 包好 forward(`wrapper.py:148-154`),首次调用触发 dynamo 一次 trace、丢全部 guards → 产出单张 FX GraphModule(唯一符号维 num_tokens),交 backend(详见第 5 章)。

**L3 vLLM 中端。** 上游给我单张 FX 图(`vllm/compilation/backends.py:1020`(`VllmBackend.__call__`))→ 我执行六步流水线(与代码顺序一致,全书统一表述):

1. ① 计算 cache hash(env 因素+config hash+traced_files 文件内容+compiler hash)并定位缓存目录(backends.py:1031-1079)
2. ② configure_post_pass:向 Inductor config 注入两个钩子 pre_grad_custom_pass 与 post_grad_custom_post_pass(backends.py:1171, 定义于 :934)
3. ③ split_graph:按 splitting_ops 切分 FX 图(backends.py:1179)
4. ④ PiecewiseCompileInterpreter.run:逐 piece 构造 PiecewiseBackend 并把所有 range 一次编完(backends.py:1222)→ 保存 CompilerManager 缓存(:1228)
5. ⑤ generate_execution_code + compile_execution_fn:生成纯 Python 组装代码并 exec(backends.py:1279-1289)
6. ⑥ 组装 VllmSerializableFunction(必要时包 copy_and_call)返回(:1291-1339)

产物是 **split_gm(切分图模块)**:attention 类算子所在的 splitting piece 保留源码形态,可编译 piece 的属性已被编译产物替换(`backends.py:766` 直接改写 `self.module.__dict__[target]`)。按官方文档口径,Llama 切分后只有 3 类唯一子图(pre-attention / 每层重复 / post-attention)——已与源码机制核对一致(切分细节详见第 6 章)。

**L4 Inductor 后端。** 上游给我 split_gm 的一个个可编译 piece(`vllm/compilation/piecewise_backend.py:86`(`PiecewiseBackend.__init__`))→ 我在构造函数里就把该 piece 的全部 range 一次编完(:190 调 :245 `compile_all_ranges`),编译请求经 `CompilerManager.compile`(`backends.py:264`)驱动 **`CompilerInterface`(编译器接口,`vllm/compilation/compiler_interface.py:27`)** 的三实现——`InductorAdaptor`(:449)调 `compile_fx`、`InductorStandaloneAdaptor`(:251)走 `standalone_compile`、`EagerAdaptor` 供调试,vLLM 的自定义 pass 经两个钩子注入 → 产出每 piece × 每 range 一个 compiled artifact(适配与缓存细节详见第 8、9 章)。

**L5 运行时执行层。** 上游给我 execution_code 字符串与编译产物(`vllm/compilation/codegen.py:131`(`generate_execution_code`)、`:165`(`compile_execution_fn`))→ 我生成纯 Python 的 **execution_fn(执行函数,绕开 FX GraphModule 的解释开销)**;**`CUDAGraphWrapper`(CUDA Graph 包装器,`vllm/compilation/cuda_graph.py:145`)** 在启动期按桶 capture、serve 期 replay;**`CudagraphDispatcher`(图分派器,`vllm/v1/cudagraph_dispatcher.py:15`)** 每步按 num_tokens 与 LoRA 状态选模式选桶(:235 `dispatch`)→ 产出 serve 期每步调用的 callable。

### 3.3.2 启动时间轴:编译到底发生在什么时候

五层图回答"谁给谁供货",时间轴回答"何时发生"。编译不在 import 时、不在 serve 期,而是全部挤在启动期的一段严格工序里:

> `gpu_worker.py:435`(`load_model`)把权重装进 GPUModelRunner 并触发 `gpu_model_runner.py:5303`(`load_model`)→ 权重就位后,按模式决定包装优先级(:5449-5478:breakable → FULL(has_full_cudagraphs)→ UBatchWrapper)→ 产出"已包装、未编译"的模型,交 `compile_or_warm_up_model`(`vllm/v1/worker/gpu_worker.py:679-718`)。

承重墙代码是 warmup 尺寸的推算:


### 3.3.3 唯一直接 torch.compile 调用点辨析

读源码时容易困惑:全书主线里,`torch.compile` 到底在哪里被调用?答案是有两处入口、一条主线。主线 **VLLM_COMPILE** 只有一处直接调用,藏在包装器的构造函数里:`TorchCompileWithNoGuardsWrapper.__init__`(`vllm/compilation/wrapper.py:72-160`)在模型实例化时执行——

```python
# vllm/compilation/wrapper.py:148-154 (v0.27.1)
self._compiled_callable = torch.compile(
    compiled_ptr,          # 即模型的 forward
    fullgraph=True,        # 禁止 graph break
    dynamic=False,         # 不自动 dynamic,符号维由装饰器显式声明
    backend=backend,       # VLLM_COMPILE 时为 VllmBackend
    options=options,       # 含 guard_filter_fn 丢 guards
)
```

注意它只"包"不"编":真正触发 dynamo trace 的是首次 forward 调用(`decorators.py:502` 的 `__call__` 判定 `self.compiled` 为 False 才走编译路径)。另一条路 **STOCK_TORCH_COMPILE** 不用装饰器触发编译(`do_not_compile` 含该模式,`decorators.py:390-395`),改由模型执行器在 load_model 末尾直接调用 nn.Module 的 compile:

```python
# vllm/v1/worker/gpu_model_runner.py:5435-5445 (v0.27.1)
if (
    self.vllm_config.compilation_config.mode
    == CompilationMode.STOCK_TORCH_COMPILE
):
    ...
    backend = self.vllm_config.compilation_config.init_backend(self.vllm_config)
    compilation_counter.stock_torch_compile_count += 1
    self.model.compile(fullgraph=True, backend=backend)
    return
```

两条路经由同一个分发点 `init_backend`(`vllm/config/compilation.py:1062`)汇入一个 backend:STOCK 与 DYNAMO_TRACE_ONCE 返回后端名字符串(默认原生 Inductor,:1090-1096),VLLM_COMPILE 返回 `VllmBackend`(:1104)。也就是说,STOCK 汇入的是上游原生 Inductor,L3 整层被绕过;主线汇入 VllmBackend,再由它经适配器驱动 Inductor——同一个 torch.compile 机制,两种集成深度,这正是第 1 章"三宗罪"里原生路径不可直接上线的制度化出路(模式语义详见第 4 章)。

### 3.3.4 三条正交轴线:机制的坐标系

五层图是纵向分层,还需要一把横向的尺。全书反复出现三条彼此正交的轴线,任何机制都能被三根坐标钉死:

```text
                    编译期                      运行时
        ┌─────────────────────┬─────────────────────┐
图内    │ 逐 range Inductor 编译│ attention 边界算子   │
        │ fusion pass 区间门控 │ 在图内位置取当步元数据│
        ├─────────────────────┼─────────────────────┤
图外    │ cache hash 建缓存目录│ CudagraphDispatcher │
        │ 生成 execution_code │ 查表选桶并 replay    │
        │ 并 exec             │ lm_head 与采样       │
        └─────────────────────┴─────────────────────┘
 轴3 shape: 静态 = 尺寸桶与单尺寸 Range   符号 = 区间 Range 产物
```

- **轴 1 编译期 vs 运行时**:机制醒着的时段。六步流水线、pass、代码生成全在编译期;dispatch、replay、ForwardContext 注入全在运行时。判据很简单——不变量 (d) 说 serve 期零 Python 编排,于是凡在 serve 路径上的,都只能是"查表+调用"。
- **轴 2 图内 vs 图外**:机制相对编译图边界的位置。图内享受融合与捕获,图外保留控制流自由——lm_head 与采样永远在图外(详见第 2 章),attention 永远在图内边界处:它在 FX 图里是节点,但 PIECEWISE 模式下其所在的 splitting piece 不编译不捕获,运行时经模块级全局加 `set_forward_context` 上下文管理器设置的 ForwardContext 取当步元数据(`vllm/forward_context.py`,"图是静态的、信息是动态的")。
- **轴 3 静态 shape vs 符号 shape**:产物以什么形状知识编译。单尺寸 Range 开 max_autotune 全静态,区间 Range 长出符号维;CudagraphDispatcher 只在静态桶一格里工作。这根轴就是 P7(shape 是推理编译的核心矛盾)的坐标化。

举两个落格的例子:fusion pass = 编译期 × 图内 × 按 range 门控(第 10 章);`CudagraphDispatcher` = 运行时 × 图外 × 静态桶(第 12 章)。三轴正交意味着它们可以独立演进——换一个 pass 不影响运行时,换捕获桶表不影响图内融合,这是 P6(平台与后端可插拔)的几何表达。

### 3.3.6 20 步编号清单:一条 forward 从 Python 调用到 GPU kernel

下面这份编号清单是后续每章的"当前位置"参照,编号全书稳定(1-4 模型层、5-8 dynamo、9-13 中端、14-17 后端、18-20 运行时):

1. 模型类在 models 目录定义,forward 是普通 Python(`llama.py:310` 起)。
2. `@support_torch_compile` 注入包装基类、声明唯一符号维(`decorators.py:118,331`)。
3. `load_model` 装权重并按模式与图模式装外层 wrapper(`gpu_model_runner.py:5303,5449-5478`)。
4. 启动期 `_dummy_run` 发起首次 `self.model(...)` 调用(`gpu_model_runner.py:5830,6156`)。
5. 包装器 `__call__` 发现未编译,先标注动态维再调编译入口(`decorators.py:502`;`wrapper.py:171`)。
6. dynamo 以 fullgraph、dynamic=False 包住的 forward 开始一次 trace(`wrapper.py:148-154`)。
7. guards 全丢,`fail_on_recompile` 断言此后永不 re-trace(`wrapper.py:120-122,195`)。
8. 产出单张 FX GraphModule,作为 backend 入参进入 `VllmBackend.__call__`(`backends.py:1020`)。
9. ①算 cache hash 四要素并定位缓存目录(`backends.py:1031-1079`)。
10. ②configure_post_pass 注入 pre_grad_custom_pass 与 post_grad_custom_post_pass 两钩子(`backends.py:1171,934`)。
11. ③split_graph 按 splitting_ops 切图(`backends.py:1179`)。
12. ④PiecewiseCompileInterpreter.run 逐 piece 构造 PiecewiseBackend(`backends.py:1222`)。
13. 产出 split_gm,可编译子模块属性即将被产物替换(`backends.py:766`)。
14. PiecewiseBackend 在构造时登记全部 range 并一次编完(`piecewise_backend.py:190,245`)。
15. CompilerManager.compile 先查缓存,未命中走 CompilerInterface 适配器(`backends.py:264`;`compiler_interface.py:27`)。
16. InductorAdaptor 调 compile_fx,AOTAutograd 与 lowering 展开(`compiler_interface.py:449,492`)。
17. vLLM pass 经两钩子在 pre/post_grad 处运行,融合发生;产出每 piece × 每 range 一个 artifact。
18. ⑤⑥生成并 exec 纯 Python execution_fn,包成 VllmSerializableFunction 返回(`backends.py:1279,1287,1295`)。
19. capture_model 按降序清单录静态图集,结束即锁定(`gpu_model_runner.py:6814,6900`)。
20. serve 期:step → execute_model → dispatch 查表 → replay,kernel 上 GPU(`core.py:584`;`gpu_model_runner.py:3977,3903`)。

注意这份清单把编译期(1-18)与运行时(19-20)串在一条线上——它讲的是"一个 forward 的完整一生",不是"serve 期的某一步"。serve 期的每一步只走第 20 步;前 19 步的全部产出,都以查表可及的形式沉淀在第 20 步的周围。

## 3.4 本章小结

- 五层各守一份产物契约:forward → FX 图 → split_gm → artifact → callable。
- 编译全部挤在启动期:dummy run 触发,capture 锁定收尾。
- 全书主线仅一处直接调用 torch.compile:wrapper.py:148。
- 三条正交轴线可定位一切机制:工期、边界、shape。
- 20 步清单是全书通用的当前位置参照。

本机制(全景分层与时间轴)服务于 P1(compile once, run forever)、P2(不变量换性能)与 P5(显式优于隐式),并把 P7 提前钉在坐标系的第三根轴上。下一章(第 4 章)先认识用户可拨动的旋钮:三个正交枚举与 -O 优化级别。它们决定本章时间轴上每一步是否发生、以何种规模发生,是这张全景图的第一组可配置参数。
