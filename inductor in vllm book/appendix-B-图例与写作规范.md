# 附录 B 图例与写作规范

> 本附录是全书写作规范的唯一权威(source of truth)。每章写作与审校均以本附录为准。

## B.1 章节模板(五段式,强制)

每章严格按以下结构组织(节号用 `N.0`~`N.4`,N 为章号):

```markdown
---
chapter: N
part: <I~VI>
title: <章标题>
status: draft | review | done
difficulty: ★~★★★★★
depends: [章号列表]
---
# 第 N 章 <标题>

<!-- 6 行 ASCII 位置导航图(见 B.4) -->

## N.0 本章俯瞰
<!-- 300~500 字。以一个问题开场,第一段末尾给一句答案预告。
     说清本章解决什么问题、为什么存在。不使用本章新术语。
     正文之后附一张编译管线定位图(见 B.4)。 -->

## N.1 最小前置知识
<!-- 只列本章用到的 3~5 个概念,每个 2~3 句,给跳转链接。
     原则:够用就行——理解本章所需的最小集合,不多不少。 -->

## N.2 设计思想与设计哲学
<!-- 先讲"为什么这样设计",再讲怎么做。标注【哲学时刻】的段落

## N.3 具体流程(流水线视角)

## N.4 本章小结
<!-- 3~5 条要点(每条 ≤25 字)+ 一句"本机制服务于哪条哲学命题"
```

## B.2 步骤叙事三段式与流水线产物句式(强制,适用于 N.3 具体流程)

**N.3(具体流程·流水线视角)的每个机制/工序小节**按**三段式**组织叙事,顺序不可颠倒;其余各节(N.0/N.1/N.2/N.4)参考其思想——目的先行、读者先有坐标——形式随节型自定:

1. **目的**——这一步回答什么问题、为什么必须存在;先于一切细节给出。
2. **思想/流程**——核心思想一句话,再展开流程;流程环节用下述产物句式描述。
3. **衔接**——产出交给谁、引出下一环(指向下一小节或下一章)。

产物句式(三段式中"流程"环节的内部格式):

> **上游给我什么**(产物类型)→ **我做什么加工**(算法/变换)→ **我产出什么**(产物类型 + 去向)

块引内**不放源码行号**;确需的锚点按 B.3 的密度规则放正文,其余下沉章末"本章源码索引"。

示例:
> `PiecewiseCompileInterpreter` 从切分拿到 `split_gm`(带 `submod_N` 子模块的 GraphModule)→ 逐个子模块构造 `PiecewiseBackend` 并全量预编译 → 编译产物替换 `split_gm` 的 submodule 属性,供后续 codegen 直接引用。

## B.3 代码与锚点规范

- **源码锚点双保险**:`路径:行号`(`符号名`)。行号随版本漂移,符号名可重定位。全书基线 **vLLM 0.27.1**。
- **行号下沉规则**:正文源码锚点密度 ≤2 个/千字;一句话内出现 ≥2 个 `:行号` 锚点即视为超标——多锚点与行号区间细节一律下沉章末"本章源码索引"(附录 C 已有程序化备份,信息不丢)。块引(B.2)内不放行号。
- 代码片段:每章 ≤2 段,每段 ≤15 行;片段上方标注 `# vllm/compilation/backends.py:1020-1046 (v0.27.1)`;只贴"承重墙"代码(承载设计决定的那几行),其余用自然语言或伪代码。
- **命令块规则**(实践章,第 15 章):命令块不受源码片段上限约束,但每块 ≤6 行,且须配"预期看到(示意)"观察点;禁止把命令块当源码走读的载体。
- 术语:类名/函数名/字段/env var/文件名一律英文原文;首次出现加粗并给中文释义(如 **guard(守卫条件)**),此后只用英文。dynamo、fake tensor、functionalization、max_autotune、capture/replay 等通用词直接用英文。
- 章间引用:`[第 9 章](09-逐range编译与Inductor对接.md)` 或"(详见第 5 章)";禁止"如前所述"式无锚点回指。
- **示意标注统一**:手推/非真实 dump 标注「示意图」,真实 dump 标注「真实产物摘录」,命令的预期输出允许行内"(示意)";不得混用【示意】/「示意」等变体。

## B.4 ASCII 位置导航图(每章开头,统一模板)

全书 15 章按编译栈阶段排成 6 行,当前章以 `◄==` 追加标注。模板(以第 9 章为例,其余章只挪动 `◄==`):

```text
I   背景:   [1 为何compile] → [2 V1引擎] → [3 编译栈全景]
II  前端:   [4 配置体系] → [5 Dynamo一次捕获]
III 中端:   [6 Piecewise切分] → [7 算子边界与vllm_ir]
IV  后端:   [8 VllmBackend] → [9 逐range编译]◄== → [10 Pass与融合]
V   运行时: [11 代码生成] → [12 CUDA Graph] → [13 缓存与AOT]
VI  收官:   [14 设计哲学] → [15 动手实践]
```

- ASCII 图行宽硬上限 **78 列**;只用于局部示意(单机制输入→变换→输出、导航图),复杂架构一律 Mermaid。

### 编译管线定位图(N.0 内,每章一张,强制)

每章 N.0 正文之后放一张 ASCII **编译管线定位图**,作为读者的定位坐标。规则:

1. **统一骨架**:以全书统一的编译管线骨架为底;非本章部分逐章保持同一段粗粒度模板(模块化一行带过),让读者在任何一章都能认出同一张地图。
2. **本章展开**:本章讲解的区段展开一级(细到小节/机制名),并以 `◄== 本章` 标注当前位置;展开区段与本章 N.3 的小节结构对应。
3. **换轴条款**:非栈章节换轴定位——第 1、2 章用服务链(调度 → forward → 采样),第 3 章为全栈导览(标注各块由哪章细讲),第 14 章标注七命题在管线的落点,第 15 章标注外部观测点。
4. 行宽 ≤78 列(汉字按 2 列计);与 B.4 章节导航图互不替代——导航图答"读到哪一章",定位图答"内容落在编译栈哪一站"。

## B.5 Mermaid 图规范

### 图型选择(一一对应,不混用)

| 图型 | 用途 | 约束 |
|---|---|---|
| `flowchart` | 架构/分层/数据流 | 分层图一律 `TB`,流水线图一律 `LR` |
| `sequenceDiagram` | 有明确参与方的控制流 | 参与方 ≤6 |
| `classDiagram` | 核心类关系 | 只画本章涉及的 3~7 个类,禁止全量 |
| `stateDiagram-v2` | 生命周期/状态迁移 | capture→replay、缓存命中、range 匹配等 |

### 颜色语义(全书统一,经 `class` + `style` 声明)

| 颜色 | 含义 | Mermaid class 名 |
|---|---|---|
| 蓝 `#3B82F6` | vLLM 自身代码 | `vllm` |
| 橙 `#F59E0B` | torch / Inductor / dynamo 上游 | `torch` |
| 绿 `#10B981` | 编译产物 / 缓存 / 生成的代码 | `artifact` |
| 灰 `#6B7280` | 外部系统(CUDA / NCCL / 文件系统) | `ext` |
| 红 `#EF4444` | monkey-patch / 危险点 / 陷阱 | `danger` |

每个 flowchart/class 图开头声明一次(可直接复制):

```
classDef vllm fill:#DBEAFE,stroke:#3B82F6,color:#1E3A8A
classDef torch fill:#FEF3C7,stroke:#F59E0B,color:#78350F
classDef artifact fill:#D1FAE5,stroke:#10B981,color:#064E3B
classDef ext fill:#E5E7EB,stroke:#6B7280,color:#374151
classDef danger fill:#FEE2E2,stroke:#EF4444,color:#7F1D1D
```

### 线型语义

- 实线 `-->`:编译期数据流(产物传递)
- 虚线 `-.->`:运行时调用流
- 粗线 `==>`:本章主线索

### 节点形状语义

| 形状 | 语法 | 含义 |
|---|---|---|
| 圆角矩形 | `A[ ]` | 模块 / 类 / 函数 |
| 菱形 | `A{ }` | 决策 / 分支 |
| 圆柱 | `A[( )]` | 缓存 / 存储 |
| 体育场形 | `A([ ])` | 入口 / 出口 |

### 渲染兼容硬规则(违反即渲染失败)

1. 节点文本**禁用**半角括号 `()`、冒号 `:`、双引号 `"`——用全角 `()`、中文冒号或空格替代
2. `sequenceDiagram` 的别名只用 ASCII 字母数字
3. `classDiagram` 的关系符号与标签间必须有空格:`VllmBackend *-- CompilerManager`
4. 图内文本优先中文(读者友好),类名/函数名保持英文

### 数量要求

每章 ≥1 张正式 Mermaid 图 + ≥1 张 ASCII 小图(或第二张 Mermaid);第 3、12、15 章可 3 张。

## B.6 字数与难度

- 每章正文(不含 YAML/代码块/图)3000~5000 字;第 9、12 章允许至 5000+
- 难度标注:★(通识)~★★★★★(需反复研读)
- 前言约 1500 字,阅读指南约 1200 字

## B.8 标注块与正文标点

- **【哲学时刻·P#】**:全书七条命题(第 14 章)在本章的落点,P# 为命题编号;每章 ≤3 处。
- **【设计品味】**:七命题之外的工程品味判断;每章 ≤3 处。
- **正文标点**(全书统一,防止漂移):半角逗号 `,` 与分号 `;`、全角括号 `()`、中文句号 `。`、全角冒号 `:`、弯引号 `""` 表强调或引用;行内代码一律反引号。ASCII 导航图与 mermaid 节点内仍按各自规则(B.4/B.5)。

## B.9 上游对照叙事(全局)

凡涉及 vLLM 对上游(torch / Inductor / dynamo / 原生 CUDA Graph)的定制,章节须按**五问**推进:

1. 要干什么(这个机制解决什么问题);
2. 上游为什么做不到(其对应物、管辖边界与隐含假设);
3. gap 在哪(vLLM 部署形态与上游假设错位的具体点,不可空喊"性能不行");
4. 思路与思想(推广上游单图之招 / 接管上游机制 / 垫适配层);
5. 方案(落到哪个类、哪道工序)。

上游没有对应物的机制,第 2/3 问改答"上游为什么没有这个问题"。**适用于所有章节,不限 N.3**;细则与正反例见书目录内 `vllm-book-style.md` §5。
