## 11.0 本章俯瞰

第 9 章结束时,流水线手里有了一张特殊的图:每个可编译片段都已被偷换成编译产物,attention 所在的片段保持原样。但若就此收工,serve 期每一步仍要靠 FX 的模块调用机器去驱动这张图——每调一个子模块都要经过一次完整的模块调用协议,还要按名字做属性查找;而 decode 的步长是微秒量级,这些固定开销恰恰是全书立志消灭的对象。本章讲编译的最后一道工序:不再"解释"这张图,而是把它整体编译成一段纯 Python 源码,交给解释器执行,并把这段源码连同图、常量表、子模块清单一起打包成可落盘的形态。答案预告:这招并非 vLLM 首创——Inductor 编译单图时,交给运行时的本来就不是 FX 图而是自己生成的 wrapper;vLLM 做的是把同一招推广到切分造出的拼接层,并一举换来三件事——出问题时工程师能直接读到运行中的真相源、整个产物可以整体序列化以支撑下次启动免编译、拼接层的 Python 开销被压到"一行一次函数调用";此外,源码里显式写下的释放语句还把中间显存的回收时机从运行时的偶然变成了编译期的决定。

先把本章放进整条编译管线:

```text
torch.compile(model)
│
├─ dynamo 一次捕获 ─▶ 整图 FX
├─ 切分 ─▶ submod_0..N
├─ 全量预编译(片段 × range)
│    └─ compile_fx:AOT → pass → Inductor
│         └─ Inductor 产物:可序列化 kernel artifact ◄== 本章上半场
│
├─ 造外壳 ◄== 本章下半场
│    ├─ 执行代码生成:把拼接图抄成一份可序列化源码
│    ├─ consts / submod_callables 装配
│    └─ 反序列化装载:温启动直接取用
│
└─ serve 期:查 range 执行
```

## 11.1 最小前置知识

- **split_gm**(拼接图):`split_graph` 产出的 FX GraphModule,子模块命名 `submod_0..N`;可编译片段的属性已被 `PiecewiseCompileInterpreter` 偷换成编译产物,splitting piece 仍是普通 GraphModule(详见第 6 章)。
- **nn.Module.__call__ 开销**(模块调用协议开销):FX GraphModule 执行 `call_module` 节点要过完整的模块调用协议(hook 检查、属性查找等)。每步几十次调用累积成可观的 CPU 时间,是本章要消灭的对象。
- **liveness 分析**(活性分析):编译器经典前置分析,回答"每个值活到哪条语句为止"。本章用它决定在生成源码的哪个位置插入 `del`。
- **exec 与 functools.partial**:Python 内建。`exec` 把源码字符串编译成字节码并放进给定命名空间;`partial` 给函数预绑定关键字参数。两者拼出"源码即函数"的最低成本路径。
- **GraphPickler**(FX 图序列化器):torch 提供的 FX 专用 pickler,能把 GraphModule 连同节点 meta 一起序列化;vLLM 在其上叠加定制 reducer。缓存目录布局详见第 13 章。

## 11.2 设计思想与设计哲学

为什么不直接把 FX GraphModule 交给运行时,而要生成源码?回答之前,先把参照系立对:**Inductor 原生路径同样从不把 GraphModule 交给运行时。** compile_fx 把一张图编成 kernel 之后,运行时执行的是它自己生成的 wrapper——一段直接调用 kernel 句柄的 Python 前锋,FX 图退居调试位。"编译产物可以是生成的源码"这一招,Inductor 在单图内部早就在用。

但原生做法的管辖范围也止步于单图内部。图与图怎么拼接、编译结果怎么交付给运行时,torch 用的是自家机制:dynamo 字节码热换,加进程内存里的活对象(闭包、autotuner 状态);跨进程复用靠 torch 私有的 FX graph cache,默认同版本、同进程的世界——对"编一次、同进程跑到天荒地老"的训练脚本刚好够用。而 vLLM 的处境两头都不占:拼接层是切分带来的自家发明,torch 没有现成的低开销执行方案;产物还要按片段 × range 落盘、在新进程原样复活。原生机制于是在此处断成两截——活对象不可序列化,FX 机器的执行形态太贵。

所以本章的准确叙事不是"vLLM 发明了生成源码",而是**把 Inductor 的招从单图内部推广到拼接层**;下面三个理由,正是这次推广的三条推力,而非凭空的三条优点。

**理由一:可读——源码就是运行时的真相源。** serve 期出问题(某个片段没命中缓存、某个输入形状不对、某个融合没生效)时,工程师拿到的是一段与实际执行完全一致的 Python:每一行对应图中一个节点,读代码就是在读正在执行的程序。dynamo 的产物要靠反编译工具才能看懂,而这里的产物本身就是源码。这是 P5(显式优于隐式)最直接的落点:"图怎么被执行"不再隐含在 FX 机器的语义里,而是被显式写成了文本。

**理由二:可 pickle——产物能整体落盘。** GraphModule 携带代码对象与闭包,普通 pickle 存不下;GraphPickler 补齐了这条路。vLLM 把源码字符串、常量表、子模块名清单与 FX 图一并装进 **VllmSerializableFunction**(可序列化函数),整体序列化成一份 bytes——冷启动编译一次,此后每次启动直接加载(详见第 13 章)。两个动机在同一个形态上合流:字符串既是给人读的,也是给盘存的。

**理由三:零 FX 解释开销——splitting piece 以源码内联。** attention 片段不进 Inductor(详见第 6 章),若按 FX 机器执行,每步都要为它付一次 `call_module` 的完整协议;生成源码时,它被递归展开成普通的函数定义,attention 调用在最终源码里就是一行 Python。已编译片段同样只经一次列表下标取用。拼接层从"解释一张图"降为"顺序执行几十行代码"。

**del 与显存生命周期:与 Inductor 的辖区分界。** 生成的源码还顺手解决了一个 FX 时代没人负责的问题:中间激活的释放时机。FX 执行会把所有中间值持有到整图执行结束;生成源码后,每个中间值是局部变量,liveness 分析在它最后一次被消费的语句之后立刻写入 `del`——片段之间传递的真实张量,其显存归还时刻在编译期就已写死,不依赖 GC 的性情,也不依赖运行时的缓存策略。

**Inductor 内部早就有这套手艺。** 这里有一个自然的疑问:Inductor 内部不是早就有同类分析吗?确实有,而且不止一处。融合决策的地基,是 `torch/_inductor/dependencies.py` 的 `ReadWrites`/`MemoryDep` 读写依赖记录——scheduler 靠它判定"两个算子的读写是否重叠、能不能融、有没有 mutation 冲突"。liveness 则落在单图 wrapper 的代码生成里:Inductor 给单图生成的 wrapper 本身就会 emit `del`(`make_buffer_free`),并配合 memory_planning 做**死 buffer 的存储复用**——同一个已分配 buffer 因就地复用可以顶着多个名字("an allocated buffer can have many names")。"记录依赖、用完即删、地址复用"这套手艺,Inductor 在单图内部干得很完整。

**但管辖权止步于片段边界。**piecewise 的结构决定了每个 submod 独立过 Inductor;对任何一段来说,自己的输入是"调用者递进来的"(graph inputs),段内分析无权过问它们的生死;自己的输出是"要还给调用者的"(graph outputs),按定义必须活到函数返回,段产物对它做不了任何提前释放;只有段内中间 buffer,才是它 liveness 的辖区。于是缝合处的张量成了所有段的盲区:attention 段的输出,其最后消费者在下一个片段的**第一个算子**里——这个事实不存在于任何一段的图内,只存在于拼接层,也就是外层调度壳的 `node.users` 关系里:

```text
   submod_0 内部              缝合处              submod_2 内部
   Inductor 辖区          本章辖区              Inductor 辖区
   段内 buffer 复用+del ──▶ 激活的生死 ◀── 段内 buffer 复用+del
                        (谁的图里都不完整)
```

**两层 del 分层共存,同源而不重叠。** 最终产物里其实有两层 del 同时存在:内层的写在每段 Inductor wrapper 里,外层的写在 execution_fn 里——各管各的楼层,互不越界。两者的关系可以概括为同源、不重叠、协作:同源于"记录每个值活到哪条语句为止"这门编译器手艺;辖区被片段边界天然分开,Inductor 管每套房子内部的家具摆放,本章管街区之间的街道;而拼接层这一份刻意只做"提前释放"这一半——跨界激活用完即删,存储复用不归它管:段内有 memory planning,段间有第 12 章的图内存池另有安排。

**放回参照系:同一推广的第二次上演。**"生成源码"是把 Inductor 单图之招推广到拼接层的第一例,liveness 加 del 是同一模式的第二例——Inductor 在单图 wrapper 里就写 del,本章把这个动作同样推广到了拼接函数。一章之内,同一个"推广"发生了两次;Inductor 的 liveness 没有丢、也不用重造,它只是被片段边界切成了段内碎片,本章补上的是每段视野之外的缝合处。

【哲学时刻】**P1/P5:产物形态上的"显式"与"只编一次"。** 回扣全书叙事主线:decode 是 CPU/launch bound → 必须消灭 Python 开销 → 代价是编译 → 编译代价是启动时间 → 所以全部编译前置+缓存。本章是这条链的末端收口:拼接开销在编译期一次性付清(P2:用编译期的一次决定换运行时的零决策),产物是一段源码加一份清单,serve 期只剩顺序执行。而 **StandaloneCompiledArtifacts**(独立编译产物仓,`vllm/compilation/caching.py:37`)把 P1(compile once, run forever)再推进一步:每个片段×每个 shape 的产物 bytes 先算 **sha256** 再入库,哈希已存在就直接复用——同构 transformer 层切出的同构片段字节完全相同,一个 32 层模型的 per-layer 片段只编一次、只存一份(与第 6 章"Llama 全模型只有 3 类唯一子图"的口径一致)。这就是**内容寻址**(content-addressed):产物的身份由内容决定,不由名字或位置决定。P5 的"显式"在此落到产物形态——去重不靠聪明的猜测,靠把内容哈希写成存储键。

## 11.3 具体流程(流水线视角)

本章对应 VllmBackend.\_\_call\_\_ 六步流水线的第⑤⑥步(详见第 8 章):⑤ generate_execution_code + compile_execution_fn,⑥ 组装 VllmSerializableFunction(必要时包 copy_and_call)。

这两步联合回答的问题只有一个:**编译拿到的东西,怎么变成 serve 期"拿来即用"的交付物。** 它实际是三连问——怎么从图得到一段能顺序执行的源码(能算);这段源码连同产物装成什么形态,才能既落盘、又满足第 12 章的地址纪律(能存);落盘的 bytes 下次启动怎么原样复活(能复活)。本节六个小节各认领一问,前后以产物相接:

### 11.3.1 第⑤步前半:generate_execution_code

> **上游给我**:split_gm(拼接图 FX GraphModule,可编译子模块属性已被偷换,偷换机制详见第 6 章)→ **我做**:两遍式扫描——先做 liveness 预计算,再沿节点线性序逐节点生成语句 → **产出**:`(execution_code, submod_names, consts)` 三元组,交给第⑤步后半的 compile_execution_fn。

**这一步要做什么:把"解释一张图"变成"执行一段源码"。** 落到可操作,是两个必须先回答的子问题——图上每个节点翻成什么语句(翻译规则);每个中间值活到哪一行为止、del 插在哪里(释放时机)。后者为什么必须由拼接层自己判定、不能指望任何一段的段内分析,辖区上的原因见 11.2 的分界论证。

**怎么做:两遍式扫描——第一遍只记账,第二遍只生成。** 生成器本体是 **generate_execution_code_with_name**:第一遍把"谁在哪里最后一次被用"全书一次性算清,第二遍专心逐节点落笔、走一步查一步账。

第一遍是 liveness 预计算:对每个产出值的节点,取其全部使用者中位置最靠后者,把该值的名字记进"最后消费者位置 → 待删名字"的账本;最后消费者是 output 节点的值不安排删除——return 语句执行完函数栈即销毁,局部变量随之消亡,不必多此一举。第二遍沿节点线性序逐节点 emit 语句,每个节点处理完后查账:自己若是某些值的最后消费者,立刻追加一行 del,名字先排序;已贴近图尾则不再 emit,把收尾留给 return。

```text
【示意】两遍式扫描的伪代码
pass1(记账): del_after[最后消费者位置].append(节点名)
pass2(生成): for i, node in enumerate(nodes):
                 emit(node)                              # 按节点类型生成语句
                 if i in del_after and i < len(nodes)-2: # 图尾保护
                     emit("del " + sorted(del_after[i])) # 排序后删除
```

**四类节点的翻法,由"这个节点在运行时值多少钱"决定。****placeholder** 直接进函数参数表——它们是上游递来的实参,不该有任何翻译成本。**call_module** 是唯一需要判断的类别,而判据现成:先按名字取子模块,取到的若是普通 FX GraphModule,说明它是没被偷换的 splitting piece,递归调用生成器把它展开成函数定义 `__vllm_inlined_submods__N`,拼接在整个源码最前面——attention 从此就是一行普通调用;取到的已是 PiecewiseBackend 或其 cudagraph 包装,则只 emit 一行位置化引用 `__vllm_submods__[idx]`——零属性查找、零模块调用协议。这个 isinstance 判定本身就是"是否已编译"的探针:interpreter 只偷换编译清单内的子模块,留在 `_modules` 里的必然是 splitting piece——判据不需要额外记账,偷换这件事本身就是记账。**call_function** 里 `operator.getitem` 被改写为下标表达式 `x[i]`:getitem 是 FX 表达元组解包的通用手段,在源码里保留它就是为每次解包白付一次函数调用;其余算子按全名调用。**output** emit return,函数就此收口。

**什么能写进源码、什么不能。** 参数对象的改写由 **\_node\_ref**(`codegen.py:207-235`)负责:FX Node 换成变量名;list/tuple/dict 递归展开;int/float/bool/str/bytes/None 直接 repr;**其余非原始常量**(torch.device、DTensor placement 等)外提到 **\_\_vllm\_consts\_\_** 常量表、按下标引用,并按 `id()` 而非 repr 去重——不赌任何对象的 repr 能被 eval 回来;注释同时要求这些对象必须可 pickle,否则会连累整个产物落盘。最终 `generate_execution_code` 在源码前补上 `import torch\nimport operator\n` 两个 import。

**交出什么。** 一份三元组:源码字符串、子模块名字清单、外提的常量表。注意源码此刻还是文本、不是函数——让文本活过来,是下一步的事。

### 11.3.2 第⑤步后半:compile_execution_fn

> **上游给我**:execution_code 源码字符串、submod_names、consts 与 submod_callables(名字→可调用对象的映射)→ **我做**:exec 执行源码,再以 partial 绑定子模块表 → **产出**:runtime_callable(partial 对象),去向第⑥步组装。

**这一步要做什么:让源码从文本变成函数。** 11.3.1 交来的是字符串,字符串自己不会跑;而且要求"冷启动现场"与"缓存装载现场"两条不同的启动路径,能用同一份文本造出同一个函数。

**怎么做:先从图上取全"名字→可调用"的对照表,再用 Python 最朴素的两件工具——exec 与 partial——完成变身。** 对照表的收集只有一行字典推导,却承重:`getattr(self.split_gm, name)` 对每个子模块名取值,而 FX 的属性查找**先查 `__dict__` 再回退 `_modules`**(源码注释 `backends.py:1280-1282`)——于是已编译片段取到的是 interpreter 塞进 `__dict__` 的 PiecewiseBackend,splitting piece 取到的是 `_modules` 里的原图。变身由 compile_execution_fn(`codegen.py:164-204`)完成:

```python
# vllm/compilation/codegen.py:193-204 (v0.27.1,节选,注释从略)
    namespace: dict[str, Any] = {}
    if consts is not None:
        namespace["__vllm_consts__"] = consts
    exec(code, namespace)  # noqa: S102
    fn = namespace["execution_fn"]
    submods_list = [submod_callables.get(name) for name in submod_names]
    return partial(fn, __vllm_submods__=submods_list)
```

**三个承重细节。** 其一,`__vllm_consts__` 作为命名空间全局注入,顶层函数与所有内联函数共享同一张常量表。其二,`submod_names` 收集**全部** call_module 目标(含 splitting piece)以保下标稳定;生成代码只对已编译片段读 `__vllm_submods__[idx]`,splitting 片段的槽位从不被读——`.get()` 让 mega-AOT 重建路径(那里只有编译产物)以 None 占位,两条路径下标完全一致(注释 `codegen.py:198-202`)。其三,源码同时经 `trace_structured` 以 **vllm_execution_code** 之名登记为 artifact(`codegen.py:185-192`),可在 torch.compile 的调试产物里直接查看到这段代码(详见第 15 章)。

**交出什么。** runtime_callable——一个能直接调的函数。但"能算"只是及格线:落盘与输入地址稳定这两件事它一概不知;给编译结果一个同时满足两者的最终形态,是第⑥步的事。

### 11.3.3 第⑥步:VllmSerializableFunction 与 copy_and_call

> **上游给我**:runtime_callable、graph_to_serialize、example_inputs 等 → **我做**:按 cudagraph 配置决定是否再包一层输入拷贝,然后装进 VllmSerializableFunction → **产出**:VllmSerializableFunction 实例,去向:作为编译结果返回给 dynamo 装饰的 forward,serve 期每步被调用。

**这一步要做什么:给编译结果定最终交付形态。** runtime_callable 只回答了"能算";交付前还悬着两个需求——第 13 章的缓存体系要求整个结果能整体 pickle 落盘,第 12 章的 CUDA Graph 重放要求输入地址永远不变。这一步把两者封进同一个形态。

**箱子与清单。** 形态就是 **VllmSerializableFunction**(可序列化函数),它持有的字段即交付清单:graph_module(FX 图)、example_inputs、prefix、optimized_call(即 runtime_callable 或 copy_and_call)、sym_tensor_indices、execution_code、submod_names、consts、aot_autograd_config,外加从首个 SymInt 输入"偷"出来的 **shape_env**——反序列化后若要重跑编译,符号约束全靠它。运行时入口 `__call__` 只有一行:转发 optimized_call——serve 路径零额外逻辑。

**可选拷贝层:copy_and_call。** 默认无拷贝分支直接把 runtime_callable 当 optimized_call 装箱(`backends.py:1291-1305`)。当配置要求时(`cudagraph_mode != NONE` 且 `cudagraph_copy_inputs` 开启),先计算 **sym_tensor_indices**——example fake 输入里 shape 含符号维(FakeTensor)的下标;权重与静态 buffer 形状具体,不会入选——再以 **make_copy_and_call** 包一层:每次调用把运行时张量拷入常驻静态 buffer(`input_buffers[i][:runtime_shape].copy_(runtime_tensor)`),再把静态 buffer 换进实参表去调用产物;buffer 首次调用惰性 clone 出最大尺寸(主路径直接以 example_inputs 的克隆初始化)。这一层是在替第 12 章打地基:动态 shape 输入每次落进同一块常驻内存,图内地址即稳定;前缀切片让同一块 buffer 服务不同的 num_tokens。

**交出什么。** 一个既能整体序列化、又(必要时)自带地址纪律的对象,作为编译结果返回给 dynamo 装饰的 forward,serve 期每步被调用的就是它。至于这个箱子能不能真的 pickle——要看里面每个字段的脸色,那是下一节的问题。

### 11.3.4 落盘:定制 reducer 与无情的剥离

> **上游给我**:VllmSerializableFunction 实例(第⑥步组装的最终产物)→ **我做**:剥掉一切不可 pickle 或不必要的字段,FX 图与输入分别经 GraphPickler 序列化 → **产出**:一份 pickle bytes,去向:编译缓存目录(详见第 13 章)。

**这一步要做什么:把"活过的编译现场"变成能上盘的 bytes。** 序列化在这里不是免费的:箱子里的 FX 图粘着 sympy 符号函数与 fake tensor mode 这类运行时对象,直接 pickle 要么存不下、要么存下了也复活不了。这一步回答的是"什么必须带走、什么可以不带"。

**剥离原则一句话:盘上只留重建所需的最小集合,其余都是重新装载时能重新造出来的。** 据此分两层执行,各解决一层问题。

第一层 **serialize_graph_module** 解决"图怎么存":在 GraphPickler 的 reducer 上加两条定制——sympy Function 交给 torch 的 `_torch_unpickler` 按名字重建(符号函数是全局注册表里的名字,不是可拷贝的数据);FakeTensorMode 直接降为 None(反序列化后重新造一个 fake mode 即可,旧的没有必要跟过来);配套 **patch_pytree_map_over_slice** 临时把 slice 注册为 pytree 节点,让含切片的输入树能被完整遍历。第二层 **serialize_compile_artifacts** 解决"什么东西根本不该上盘",剥离原则一句话:**盘上只留重建所需的最小集合,其余都是重新装载时能重新造出来的**——pop 掉 optimized_call、shape_env、vllm_backend、_fake_mode 四个运行时字段;剥掉所有节点的 source_fn_stack 与 nn_module_stack meta(它们服务于日志与堆栈定位,不服务于重建);example_inputs 里的张量全数挪到 meta device——落盘只要 shape 元数据(即 make_copy_and_call 的 buffer 尺寸),不要真实数据。

**mega 模式的追加项。** 若开启 mega 模式,再追加逐片段产物:每个 PiecewiseBackend 经 **to_bytes** 以 `bundled_autograd_cache=True` 序列化各 range 的 runnable,由 StandaloneCompiledArtifacts.insert 按 sha256 入库,计数器只在出现新哈希时递增——去重效果可观测。mega 模式落盘的图特意选"未被偷换"的原图,因为重建时产物由 artifact store 提供,偷换过的图反而把产物焊死在 FX 属性里。

**交出什么、怎么检验。** 一份 pickle bytes,落进编译缓存目录。剥离到什么程度才算够,检验标准只有一个——下一节的两条重建路,能否把它原样跑起来。

### 11.3.5 反序列化:两条重建路

> **上游给我**:pickle bytes(来源缓存目录)→ **我做**:deserialize_compile_artifacts 判路——常规路径惰性重跑编译,mega 路径零编译重建 → **产出**:可立即服务的 VllmSerializableFunction,去向:替代本次启动的整条编译流水线。

**这一步要做什么:从 bytes 恢复一个可立即服务的函数,并在"恢复快"与"落盘瘦"之间选边。** 两条路的存在本身就是一个设计陈述:常规路径赌"重跑编排很便宜",落盘因此可以瘦;mega-AOT 路径把产物 bytes 全部随包携带,启动即零编译。两条路从同一份 pickle bytes 出发,分工如下:

| | 常规路径 | mega-AOT 路径 |
|---|---|---|
| 入口 | deserialize_compile_artifacts | reconstruct_serializable_fn_from_mega_artifact |
| 何时用 | 默认;缓存里只有图与源码 | 落盘时开了 mega 产物(要求 standalone 编译开启) |
| 重建什么 | graph_module 反序列化并 recompile;optimized_call 是惰性闭包,首次被调用时才在 `tracing(TracingContext(fake_mode))` 里新建 VllmBackend 重跑整条六步流水线 | 零编译:load_all 以 ThreadPoolExecutor 并行反序列化全部产物;逐子模块以 `graph=None, compiled_runnables=...` 重装 PiecewiseBackend,复用 wrap_with_cudagraph_if_needed 包上捕获包装;再对落盘的 execution_code **重跑 compile_execution_fn** 得到 runtime_callable,必要时重挂 make_copy_and_call |
| 代价 | 首次调用多付一次流水线编排(dynamo 不再 trace,各 piece 命中 handle) | 产物 bytes 随包携带,体积换零编译 |

惰性是常规路径的关键一笔,而且必须是惰性:缓存目录的计算依赖 traced_files,而它要等源码校验完成后才就绪,装载时立刻重跑反而无账可查;`finalize_loading` 因此给温启动补了一个急切装载的入口(第 13 章的 AOT 路线用它)。mega 路径的 docstring 明说这是 PiecewiseCompileInterpreter 的镜像流程——同一段组装逻辑,一处从 FX 图出发、一处从缓存产物出发。

**交出什么。** 无论哪条路,产物都是同一个 VllmSerializableFunction,它替代了本次启动的整条编译流水线。至此⑤⑥两步闭环;所有规则叠加在一起长什么样,11.3.6 用一个 2 层模型手推验算。

### 11.3.6 手推主例:2 层 5-piece 模型的 execution_fn

取第 6 章 6.3.5 的 2 层 5-piece 模型(残差传递从简),按 11.3.1 的规则手推生成的完整源码:

```python
# 【示意图 · 依 codegen 规则手推,非真实 dump】2 层 5-piece 的 execution_fn
import torch
import operator

def __vllm_inlined_submods__1(q_rope, k_rope, v):            # splitting piece 递归内联
    attn_output = torch.empty_like(q_rope)                   # 空分配节点
    torch.ops.vllm.unified_attention_with_output(            # attention 就是一行 Python
        attn_output, q_rope, k_rope, v, "layer.0", 0.05)
    return attn_output

def __vllm_inlined_submods__3(q1_rope, k1_rope, v1):         # 第二层,同构但独立内联
    ...                                                      # 与 __vllm_inlined_submods__1 相同

def execution_fn(hidden_states, positions, *, __vllm_submods__):   # 参数表 = placeholder
    submod_0_out = __vllm_submods__[0](hidden_states, positions)   # 已编译片段,位置化引用
    q_rope = submod_0_out[0]                                 # operator.getitem → 下标
    k_rope = submod_0_out[1]
    v = submod_0_out[2]
    del submod_0_out                                         # 元组的最后消费者是第三个下标行
    attn_output = __vllm_inlined_submods__1(q_rope, k_rope, v)     # 直接函数调用,零 FX 机器
    del k_rope, q_rope, v                                    # sorted 排序后的 del
    submod_2_out = __vllm_submods__[2](attn_output)
    del attn_output
    q1_rope = submod_2_out[0]
    k1_rope = submod_2_out[1]
    v1 = submod_2_out[2]
    del submod_2_out
    attn_output_1 = __vllm_inlined_submods__3(q1_rope, k1_rope, v1)
    del k1_rope, q1_rope, v1
    hidden_states_out = __vllm_submods__[4](attn_output_1)   # 此处不 del:已是倒数第二节点
    return hidden_states_out                                 # 消费者是 output,return 收尾
```

逐段读。**参数表**就是顶层图的 placeholder 序列,`__vllm_submods__` 是 keyword-only 参数,由 partial 绑定。**第一行调用**是位置化的已编译片段:没有属性查找,没有模块调用协议,只有一次下标取用加一次调用。**内联 attention 行**是 splitting piece 被递归展开的结果——两层各自内联成独立函数(下标 1 与 3 稳定),函数体内 attention 调用是一行普通的算子调用。**del 行**出现的位置各有序列:`del submod_0_out` 紧跟第三个下标行(元组的最后消费者);`del k_rope, q_rope, v` 跟在 attention 调用后,且名字按字典序排列(k 在 q 前)——这正是 `sorted()` 的痕迹;而 `attn_output_1` 之后**没有** del,因为消费它的调用已是倒数第二个节点,`i < len(nodes) - 2` 不成立。**return** 收走最终值,被 output 消费的值一律不安排删除。

```text
【示意图】顶层拼接图的 liveness 落点(2 层 5-piece,位置=节点序号)
位置 语句                                    本行语句后的 del
--------------------------------------------------------------
0-1  hidden_states, positions  ← placeholder,进参数表
2    submod_0_out = __vllm_submods__[0](...)
3-5  q_rope/k_rope/v = submod_0_out[0..2]   5 后 del submod_0_out
6    attn_output = __vllm_inlined_submods__1(...)  del k_rope,q_rope,v
7    submod_2_out = __vllm_submods__[2](...)       del attn_output
11   attn_output_1 = __vllm_inlined_submods__3(...)  del k1_rope,q1_rope,v1
12   hidden_states_out = __vllm_submods__[4](...)  不 del:已近图尾
13   return hidden_states_out                      不 del:output 消费
```

对照真实规则再核一遍:每段激活在最后一次消费后立即归还显存;同构的第二层没有任何特殊待遇——这正是产物可按片段内容寻址去重的前提:源码结构相同、产物 bytes 相同、sha256 相同,一份存储服务所有层。

## 11.4 本章小结

- 生成源码之招承自 Inductor 单图 wrapper,本章推广到拼接层。(P1、P5)
- 三理由:可读、可 pickle、零 FX 解释开销。(P5、P1)
- liveness 把缝合处激活的释放写进源码语义。(P2)
- 段内 del 归 Inductor,缝合处归本章,两层共存。(P2)
- splitting piece 递归内联,attention 就是一行。(P3、P2)
- 非原始常量外提 \_\_vllm\_consts\_\_,按 id() 去重。(P5)
- 产物按 sha256 内容寻址,同构层只存一份。(P1)
- 反序列化两路:惰性重跑与 mega-AOT 零编译。(P1)

本机制集中服务于 P1(compile once, run forever)与 P5(显式优于隐式):拼接逻辑在编译期一次性变成可读、可 pickle、可去重的源码产物,serve 期只剩顺序执行与查表。下一章(第 12 章)进入运行时:这些产物如何被 CUDA Graph 捕获、重放,并按 batch 桶分派。本章埋下的 copy_and_call 常驻 buffer 与 sym_tensor_indices,正是捕获与重放得以成立的第一块地基。
